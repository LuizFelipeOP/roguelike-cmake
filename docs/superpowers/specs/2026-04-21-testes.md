# Spec — Infraestrutura de Testes

**Data:** 2026-04-21  
**Fase:** Transversal (cobre Phases 1–6)  
**Status:** Aprovada

---

## Objetivo

Adicionar uma suíte de testes automatizados ao projeto roguelike para garantir que as funcionalidades já implementadas continuem funcionando à medida que novas phases são desenvolvidas (regressão).

---

## Framework escolhido

**doctest v2.4.11** — integrado via CMake `FetchContent`.

Motivos:
- Header-only: sem dependência de biblioteca compilada separada
- Sintaxe simples e legível (`TEST_CASE`, `CHECK`, `REQUIRE`)
- Integra nativamente com CTest (`doctest_discover_tests`)
- Baixo overhead de compilação comparado ao Google Test

---

## Integração com o build

- `FetchContent_Declare` + `FetchContent_MakeAvailable` no `CMakeLists.txt` raiz
- Novo target executável: `roguelike_tests`
  - Sources: todos os `.cpp` de `src/` **exceto** `src/main.cpp`
  - Sources de teste: todos os `.cpp` em `tests/`
  - `target_include_directories`: `src/` (mesmo caminho do target principal)
  - `target_link_libraries`: `doctest::doctest`
- `enable_testing()` + `doctest_discover_tests(roguelike_tests)` para integração com `ctest`

---

## Modificações em código de produção necessárias

### `Game.hpp`

Para permitir testes de integração via subclasse de teste:

| Mudança | Motivo |
|---|---|
| `render()` → `virtual void render()` | Subclasse pode sobrescrever com noop (sem I/O de console) |
| `descerAndar()` e `inicializarAndar()` → `protected` | Acessíveis pela subclasse de teste |
| Adicionar `getAndarAtual() const` (protected) | Verificar estado interno sem expor na API pública |
| Adicionar `getNumEnemies() const` (protected) | Idem |
| Adicionar `getNumItems() const` (protected) | Idem |

### `Player.hpp` / `Player.cpp`

| Mudança | Motivo |
|---|---|
| `adicionarObserver()` — adicionar guard contra duplicatas | Corrigir bug identificado na Phase 6; permitir teste de anti-duplicação |

Guard: antes de `push_back`, verificar se o ponteiro já existe no vetor `observers_`:
```cpp
void Player::adicionarObserver(Observer* obs) {
    for (auto* o : observers_)
        if (o == obs) return;
    observers_.push_back(obs);
}
```

## Áreas cobertas e arquivos de teste

### `tests/test_entities.cpp`

**Player:**
- Atributos iniciais corretos (HP=50, ATK=5, DEF=2, level=1)
- `takeDamage` reduz HP considerando defesa (dano mínimo = 1)
- `curar` recupera HP corretamente e não ultrapassa `maxHp`
- `setPosition` muda coordenadas sem afetar atributos
- `addXP` acumula XP e sobe de nível ao atingir threshold
- `raiseAttack` e `raiseDefense` incrementam corretamente
- `isAlive` retorna false quando HP <= 0

**Goblin:**
- Andar 1: HP=6, ATK=3
- Andar 3: HP=12, ATK=5 (scaling verificado)

**Troll:**
- Andar 1: HP=12, ATK=5
- Andar 3: HP=22, ATK=9 (scaling verificado)

**Enemy (via Goblin):**
- `takeDamage` reduz HP com mitigação de defesa
- `isAlive` retorna false quando HP zerado

---

### `tests/test_factories.cpp`

**EnemyFactory:**
- `create(Goblin, ...)` retorna ponteiro não-nulo com símbolo `'g'`
- `create(Troll, ...)` retorna ponteiro não-nulo com símbolo `'T'`

**ItemFactory:**
- `create(x, y, 1)` retorna item não-nulo
- Andar 1: nenhum item de equipment (Espada, EspadaGrande, Armadura, Amuleto) — verificado em N amostras
- Andar 3: pool inclui Espada — verificado em N amostras (pelo menos 1 Espada em 200 tentativas)
- Andar 5+: pool inclui EspadaGrande, Armadura, Amuleto

> **Nota:** Testes de ItemFactory são probabilísticos por natureza. A estratégia é rodar um número grande de amostras (200) e verificar que o comportamento está dentro do esperado (itens gated não aparecem abaixo do andar mínimo).

### `tests/test_map.cpp`

**Room:**
- `center()` retorna ponto central correto
- `contains()` verdadeiro para ponto interno, falso para externo
- `intersects()` detecta sobreposição corretamente

**Map:**
- `generate()` produz pelo menos 1 sala
- Tile de parede `'#'` não é walkable; tile de chão `'.'` é walkable
- `getTile()` retorna `'#'` para coordenadas fora dos limites
- `getPosicaoEscada()` retorna posição com tile `'>'` após `generate()` (quando há mais de 1 sala)
- Fog of War: `isExplored` é `false` antes de `updateVisibility`; após chamada com posição dentro de sala, tiles da sala ficam `true`

---

### `tests/test_items.cpp`

**Strategies:**
- `CuraStrategy(10)`: player com HP 30/50 → HP 40/50
- `CuraStrategy(30)`: player com HP 30/50 → HP 50/50 (não ultrapassa maxHp)
- `BonusDefStrategy`: defesa aumenta em 1
- `AumentarATKStrategy(2)`: ataque aumenta em 2

**Inventario:**
- `adicionarItem` consumível com lista vazia → lista com 1 item
- `adicionarItem` equipamento direto no slot → `getEquipado(slot)` não-nulo
- `cheio()` retorna `true` após 5 consumíveis
- `adicionarItem` retorna `false` e não insere quando cheio
- `equipar(slot, 0)` move consumível para slot de equipamento
- `desequipar(slot)` devolve item para consumíveis
- `removerConsumivel(index)` retorna item e remove da lista

---

### `tests/test_observers.cpp`

**StatsObserver:**
- Sem nenhum equipamento: `getAttack()` e `getDefense()` sem bonus
- Com arma equipada: `getAttack()` = base + 1
- Com armadura equipada: `getDefense()` = base + 1
- Com armadura + acessório: `getDefense()` = base + 2
- Com arma + armadura + acessório: ATK+1, DEF+2

**Anti-duplicação de observer:**
- Registrar o mesmo observer 2× via `adicionarObserver`
- Chamar `notificarObservers()`
- `setAttackBonus` deve ter sido chamado exatamente 1× (verificado via efeito: ATK bonus = 1, não 2)

---

### `tests/test_game.cpp`

**GameTeste** — subclasse que sobrescreve `render()` com noop:
```cpp
class GameTeste : public Game {
protected:
    void render() override {}
};
```

**Testes:**
- Após construção: `getAndarAtual() == 1`
- Após `descerAndar()`: `getAndarAtual() == 2`
- Após `descerAndar()` novamente: `getAndarAtual() == 3`
- Após `descerAndar()`: enemies e items são recriados (listas não ficam vazias — verificado que `getNumEnemies() >= 0`, pois depende de RNG; mas `andarAtual_` incrementou corretamente)

## Convenções dos testes

- Um `TEST_CASE` por funcionalidade lógica
- `SUBCASE` para variações do mesmo cenário (ex: diferentes andares)
- `REQUIRE` para pré-condições que inviabilizam o teste se falsas
- `CHECK` para asserções que podem continuar mesmo se falharem
- Nomes em português brasileiro, descritivos: `"Player::takeDamage reduz HP com mitigação de defesa"`

---

## Como rodar

```bash
# Na pasta build/, após reconfigurar CMake:
cmake --build . --target roguelike_tests
ctest --output-on-failure
# ou diretamente:
Debug\roguelike_tests.exe
```
